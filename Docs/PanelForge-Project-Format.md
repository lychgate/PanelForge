# PanelForge — Project Folder Format (S1.1)

The on-disk layout of a PanelForge project, per spec §7.1/§7.2 and the approved
D5 resolution (owner, 2026-11-05). Implementation: `src/core/project/service.ts`
(`createProject`, `identifyProject`, `resolveProjectPath`).

## Layout

```text
MyComic/
├── project.json            ← version marker + minimal manifest (NOT the master)
├── database/
│   └── project.db          ← authoritative operational store (S1.2)
├── manuscripts/original/   manuscripts/processed/
├── characters/             locations/    objects/    styles/
├── storyboards/            artwork/generated/  artwork/approved/
├── layouts/                exports/      workflows/
└── backups/                logs/
```

The exact structure may evolve, but the project must remain understandable and portable.

## `project.json` — version marker + minimal manifest

Written atomically (tmp + rename, `0600`) by `createProject()`:

```json
{
  "formatVersion": 1,
  "projectId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "createdAt": "2026-11-05T14:00:00.000Z"
}
```

- `formatVersion` — integer format version (`PROJECT_FORMAT_VERSION`, currently `1`).
- `projectId` — UUID (`crypto.randomUUID()`), stable for the project's life.
- `createdAt` — ISO timestamp.

It is sufficient to **identify** and **version-check** a project without opening
the database: `identifyProject()` returns `NOT_A_PROJECT` (missing dir/marker),
`CORRUPT_MARKER` (unparsable or unexpected fields), `UNSUPPORTED_VERSION`
(format newer than supported — upgrade PanelForge), or the metadata.

## Canonical store (D5, approved)

- `database/project.db` (SQLite) is authoritative for operational state (S1.2).
- `project.json` is only the bootstrap manifest above — thin by design.
- JSON files inside the project (`characters/*/profile.json`, etc.) are optional
  human-readable mirrors regenerated by Core Engine export; if a mirror and the
  database disagree, **the database wins** and the mirror is regenerated.

## Paths

Stored paths are relative to the project root with `/` separators (D7) — never
absolute. `resolveProjectPath()` resolves them against the root at the
filesystem boundary and rejects absolute paths and `../` escapes.
External asset references remain an explicit, authorized exception (S1.4).

## Project metadata (S1.2)

`database/project.db` holds the metadata row (one row per project):

```sql
CREATE TABLE projects (
  project_id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  description TEXT,
  created_at TEXT NOT NULL,   -- inherited from the S1.1 marker
  updated_at TEXT NOT NULL
);
```

The `project_id` always equals the `projectId` in `project.json` (the marker is
the identity; this row is its description). `project_id`, `created_at`, and
`updated_at` are ISO timestamps; updates bump `updated_at` and leave the rest
unchanged. Writes go through the serialized queue (WAL + foreign keys + busy
timeout 5000, like the app database), and migrations are tracked in the
project database's own `schema_migrations` table.

## Schema evolution (migrations 001–019)

The project database gains tables along with each stage (tracked in
its own `schema_migrations` table; see `src/core/project/metadata.ts`).
Current head: **19**.

| Migrations | Contents |
|---|---|
| 001–002 | `projects` metadata row + S1-era store foundations |
| 003–005 | Asset registry/integrity/backup foundations |
| 006–008 | Manuscript records, normalization, chapters/scenes |
| 009–010 | Art styles + style variants (S3.11/S3.13) |
| 011 | Character profiles (S4.1) |
| 012 | Character versions (S4.2) |
| 013 | Version references (S4.3) |
| 014 | Completeness tier config (S4.5) |
| 015 | Entity bridge (`characters.source_entity_id`, S4.6) |
| 016 | Panel bindings (S4.7) |
| 017 | Version approval columns (S4.8) |
| 018 | Generation requests (S4.9) |
| 019 | Character history (S4.11) |

Manuscript-side tables (Stage 3): `manuscripts`, `normalizations`,
`chapters`, `scenes`, `entities`, `canon`. All paths stored inside
these rows are relative with `/` separators (D7); `project.json`
remains the format marker (v1).

## Stage 1 fixture (S1.11)

The end-to-end gate exercise (`tests/stage1-fixture.test.js`): a sample
project is created, copied, reopened, backed up, restored, and verified —
proving project creation, storage, asset tracking, portability, and backups
are reliable together. If any subsystem regresses (identify, metadata,
operations, paths, registry, integrity, backup), the fixture fails.
